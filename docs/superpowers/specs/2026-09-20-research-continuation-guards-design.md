# Research Continuation and Evidence Guards

## Purpose and scope

This change hardens the generic `autonomous-research` controller after issues observed while operating an external `usenix2027` case. That case is read-only: this work does not alter, delete, cite as authority, or claim that its paper proposed goal acceptance. Existing citations remain project-adaptation context only. The target is `autonomous-research`.

The controller must never declare a goal complete merely because a paper finished, tests passed, a supervisor said finish, a single hypothesis is supported, or a candidate list is empty. Completion requires a separately frozen acceptance contract and an independent coverage review. The controller also needs a durable way to pause, resume after a real changed input, and continue directly with reviewer follow-ups. Evidence cleanup must accept only controller-issued current-cycle worker outputs as new direction-owned artifacts.

## Decisions

### Acceptance and continuation control

`ResearchRunOptions` gains optional `acceptance` and `recovery` inputs. `acceptance` accepts explicit nonempty criteria with stable IDs and `evidenceKind` of `artifact`, `review`, or `scientific`; omission resolves once into a frozen **derived** contract from the full goal, profile, and rubric. A derived contract is labelled derived and is not proof that the host formally verified it. Empty criteria, duplicate or missing required IDs, an unknown evidence kind, and a silent changed acceptance input are rejected. A changed contract requires a new run or an explicit monotonic control revision.

New `research/continuation.ts` owns pure contracts and identity: frozen acceptance, criterion links, hash-bound evidence references, follow-up fingerprints, continuation decision inputs, stop reasons, and resume conditions. New `service/continuation.ts` owns durable manifests, stable paid reviewer task IDs, request-ledger reuse, read-only reviewer dispatch, and queue materialization. Its identity hashes only the frozen acceptance contract, current verifiable assessment/evidence bytes, pending queue, and explicit control revision (including caps). It deliberately excludes ledger consumption caused by the review itself and its own stop/decision files. Therefore an unchanged paused resume cannot spend again.

Coverage review is an independent, read-only `coverage-reviewer` role. Its input and output are stored as content-hashed manifests, and every paid call uses the same deterministic task ID through the existing request ledger. It can return `complete`, `followup`, `pause`, or `budget_exhausted`; it may not claim host-formal proof. Completion additionally rejects unknown scientific provenance, unsupported claims, missing/changed byte references, unresolved blockers, absent required criterion evidence, and a science criterion that fails the existing `assessEvidence` gate. At `maxCycles`, a review that can prove all criteria may complete; if review budget is unavailable, persist `budget_exhausted` rather than completing.

A cached legacy `finish` result is never authoritative after new opposing evidence, an assessment revision, or a changed coverage input: the controller must recompute current coverage before completion. Follow-up fingerprints deduplicate identical completed work, but a previously failed follow-up may retry in a genuinely new generation when its current hash-bound input/control revision differs. Reviewer-only optional `retryOf` handles a newly captured file that cannot otherwise identify its failed task: it is not a user API, and permits only `repair` with the same frozen criterion IDs and known mechanism key, plus new byte hashes and `changedCondition`. Running or unknown follow-ups cannot reopen. A derived `scientific-claims` criterion defaults to `applicability: 'when-scientific-claims'`; the full goal/profile/rubric remains frozen rather than being keyword-classified. The independent reviewer may return `not_applicable` only with a nonempty rationale and captured `sourceRefs`. The host accepts that result only when there is neither a known formal science protocol nor an explicit scientific obligation. An explicit required scientific criterion or known formal science remains applicable and must pass the existing evidence gate.

Follow-ups stay inside the frozen goal and have kind `investigate`, `repair`, or `replicate`. A revision still enters the existing strict candidate-admission path. Each item records a stable fingerprint, criterion linkage, source refs, and a concrete changed condition. It is queued durably and consumed by the next planner in the same run. An initially empty candidate set requires two finite complementary passes—an invariant/boundary pass and a cross-check/interaction pass—before `no_feasible_followup`; both must yield no compliant task. This is a local exhaustion test, not a total-round threshold: a real newly discovered gap may continue after cycle four until the frozen total max-cycles, role-call, token, or monotonic monetary cap applies. The system does not infer diminishing returns. Finished items cannot reopen because wording or an unrelated global snapshot changed; reopening requires a relevant new hash-verified source and an explicit `changedCondition`.

`pause` stores structured `stopReason` and `resumeCondition`. Terminal runs cannot rerun research, manufacture acceptance, or alter historical scientific determinations. That restriction does not revoke the user's existing authorization for `finalizeDirectionRetirement` / `advanceCleanupQueue`: their established safety checks may continue legal refutation/explicit-abandonment cleanup, audit, and tombstone metadata. An old nonterminal state may create one derived contract plus migration record and receive a new review, but cannot silently finish; a paper checkpoint and supported hypothesis cannot bypass acceptance. `recovery: { changedCondition, criterionIds?, newEvidencePaths? }` is an explicit resume route. `changedCondition` is caller-declared prose. The host verifies a monotonic control change and new run-relative bytes captured with `ResearchStore.captureSource`, then binds their hashes to the declaration. A source already bound to a known criterion identity may resume through that identity; a newly introduced source requires explicit `criterionIds` from the frozen contract. The host validates IDs and bytes, while the independent reviewer judges semantic relevance. An unlinked new file, prose-only rewrite, path/wording match, or unrelated evidence cannot defeat deduplication. Omitted recovery leaves PAUSED blocked and performs no paid work. Caps and cumulative ledger totals inherit on resume; callers cannot reset `maxCycles` with a new invocation. A controller revision creates unique `decision-C-rN` and matching `candidate-batch-C-rN`; changing a version alone is insufficient.

Publishing an accepted recovery and the corresponding run-state transition is one durable transaction or a journaled/reconcilable sequence. A crash between those writes must preserve enough canonical recovery state for resume to reuse the accepted recovery without a duplicate paid review or a new caller submission.

`startup/prepare.ts` stays read-only. A normal PAUSED run remains blocked with no action. A validated recovery intent can expose a structured `nextAction`; `scripts/session-startup.mjs` must not suggest retrying an unchanged PAUSED run. No HTTP or web execution API is added.

### Paper delivery and total completion

Paper delivery is a phase, not total goal completion. If the frozen goal includes paper criteria, an authorized paper phase may produce the paper before those criteria are marked met. The controller then captures the actual delivered artifacts and returns to total acceptance review. A `done` marker, checkpoint, compile result, or paper pipeline completion cannot independently prove the entire goal complete. A real compile log or delivered artifact may still support its specific artifact criterion when byte-captured and linked; the coverage reviewer evaluates those links in the final review.

### Evidence attribution protection

Plain model worker artifact strings are validated centrally inside `experiment/steps.ts` `runWorker`, against an issued workDir and a worker-specific frozen direction boundary/manifest: `work/cycle-XX` for service flow and `work/experiment-cycle-XX` for standalone flow. The helper resolves real paths and accepts only regular files contained in that exact root. Plain cached results require the same root/ownership proof.

The durable `runWorker` path is distinct. Its frozen graph, host `JobReceipt`, artifact manifest/declarations, collection, and source hashes are its authority; it may rehydrate canonical captured `research/sources/*` artifacts outside a plain workDir. `runtime-adapter.ts` exposes only a small helper that reuses existing collection/graph-state readers to reconstruct a completed verified action. A cached durable work stage ignores self-reported artifact strings and rebuilds the canonical host action; presence of a graph, producer label, or kind string alone proves nothing. `assessResearchCycle` repeats applicable ownership/receipt validation before `captureSource`, direction registration, or receipt creation; a failure pauses and is never downgraded to a warning followed by capture.

Continuation task work at `continuation/tasks/<fingerprint>-gN/work` is non-scientific and never writes a scientific direction/snapshot. Before its worker intent, it records a task-local baseline of existing paths/hashes. Success records an immutable validated-result receipt with exact paths/hashes; cached replay validates that receipt plus the baseline, while an old `result.json` is not authority.

Direction registration distinguishes controller-produced current-workDir output from old/mixed roots. Before capture it rejects outside-root paths, missing boundaries, preexisting unknown/shared/user files, and a same-path direction artifact with changed bytes. A result claim cannot promote `outputs`, `raw`, or pre-existing files to direction ownership merely by naming them, including a file restored to a mixed root after the boundary opens. Existing trusted controller receipt APIs that legitimately register mixed roots remain supported; they keep their existing explicit ownership/provenance semantics. Registration receipt validation is tightened so a forged receipt cannot skip these boundaries, but this is not described as arbitrary-shell isolation: host sandboxing remains a future capability.

Worker prompts prohibit deletion, movement, or overwrite of existing records and permit only creation of the current workDir artifact. Existing canonical refutation and explicit-abandonment cleanup remains intact: compact memory first, then its bounded cleanup path. Unknown metadata, old schemas, and execution errors remain unknown/non-scientific and never write `confirmed_error` memory.

## Integration seams and compatibility

The shared service flow is `service/runner.ts` -> freeze/worker/assessment -> `commitResearchDecision`. Standalone experiment paths use public helpers from `service/research-cycle.ts` where they already share worker validation, but do not gain research acceptance requirements. Scientific `ResearchSnapshot` and `assessEvidence` retain ownership of scientific claims; continuation manifests carry non-scientific investigation/review evidence separately so a missing protocol cannot demote a valid supported claim.

Prompts add a coverage reviewer with read-only tool capability and worker write constraints. Request accounting remains the source of truth for paid role calls. Tool ingress is deliberately small: `tools/index.ts` exposes optional `acceptance` and `recovery` only on `research_run`, schema `additionalProperties` remains false, and `tools/options.ts` validates/normalizes both inputs.

## Required proof

Tests must show: multiple genuine review gaps continue past four rounds; complete only follows all met, byte-verified required criteria; unknown criteria and missing refs block; unchanged PAUSED resumes make no new review call; recovery with a captured changed source revises the decision and preserves budgets/caps; no candidate, paper done, tests green, or one supported hypothesis completes alone; old paper workflow still passes; workDir/mixed-root/raw/forged-receipt cases preserve unknown ownership; a new current-workDir artifact is accepted; and execution/metadata failure does not create confirmed-error memory. Build, typecheck, and the full package test suite are required.

## Risks and rollback

The main compatibility risk is legacy snapshots with no continuation manifest. They remain readable and nonterminal; the controller writes one derived-contract migration record and reviews it, but never auto-completes. The main operational risk is an unavailable reviewer; it becomes `budget_exhausted` or `pause`, never implicit finish. Rollback is a source revert of this feature only; immutable snapshots, existing paper artifacts, cleanup tasks, and the baseline paper diff are not rewritten.
