# Current Idea Similarity Survey

## Goal

Before planning or revising research, run a durable, provider-backed search for work that is semantically close to the *current* idea. The result should make overlap, differences, uncertainty, and source coverage visible to the planner and idea reviewer without turning a similarity hit into scientific evidence or a novelty claim.

The survey addresses a specific gap in the existing flow. `brainstorm/pipeline.ts` asks a model for a broad survey and `brainstorm/deep-dive.ts` asks for a small similar-paper list, but neither guarantees varied external queries, independent provider receipts, pagination, durable retry/resume, or comparison grounded in fetched documents. In `service/runner.ts`, the legacy `!shouldBrainstorm` branch can also skip the deep-dive after a generated idea. Raising `topN` cannot repair those omissions.

## Scope and non-goals

The feature adds a bounded current-idea discovery stage for arXiv, Crossref, and Semantic Scholar. It accepts two working providers when a third is unavailable, reports provider coverage and degradation honestly, and never describes a zero-result search as proof of novelty. Semantic Scholar uses its relevance search endpoint only; a 429 is recorded as deferred/degraded while other providers continue. It does not add an embedding database, a general web crawler, a paid search dependency, a new settings UI, or automatic scientific claim assessment.

The default report is a run-scoped discovery artifact. It is available to the planner, idea generator, and idea reflexion roles as neutral candidate context. It is not a `literature-span`, does not enter the worker allowlist, does not become `Evidence`, and does not mutate a pinned index generation. If a caller explicitly elects to admit selected abstracts into the literature corpus, that operation must go through the existing object/ingest/span/index path and an explicit generation update with a reason and source-event IDs.

## Source and API contracts

Every provider attempt is an actual HTTP request made by a host adapter. A model may propose query text and follow-up queries, but it cannot create a provider result, DOI, arXiv ID, abstract, receipt, or citation seed. Each accepted result must point to a parsed response receipt whose raw response bytes are stored and hash-verified. A transport error, response-size violation, invalid parser result, rate limit, or unavailable provider is recorded as coverage degradation; it is never silently converted to an empty result.

The adapters document and test the following public behavior in source comments:

- arXiv search uses `search_query`, `start`, and `max_results`, keeps the provider's page order, and observes the documented three-second request spacing and cache guidance: [arXiv API user manual](https://info.arxiv.org/help/api/user-manual.html).
- Crossref uses `query.bibliographic`, `rows`, and bounded `offset` pagination. It does not use the deprecated `query.title`. The adapter accepts a host-supplied `userAgent`, which may contain contact information; there is no dedicated `mailto` setting: [Crossref REST API](https://github.com/CrossRef/rest-api-doc) and [Crossref rate-limit announcement](https://www.crossref.org/blog/announcing-changes-to-rest-api-rate-limits/).
- Semantic Scholar uses its graph relevance-search endpoint, treats unauthenticated throttling as expected, and records `Retry-After` or provider failure. It does not use recommendations or a bulk-page fallback: [Semantic Scholar API tutorial](https://webflow.semanticscholar.org/product/api/tutorial) and [Semantic Scholar API overview](https://webflow.semanticscholar.org/product/api).

Response bodies are bounded before parsing. The coordinator limits requests, candidates, rounds, and wall time independently of the final context-token budget. It uses an injected clock, sleep function, fetch function, and optional host callbacks so unit tests never need live HTTP or real waiting. Sleeps are interruptible and never block for more than 60 seconds at once.

## Contracts and durable state

The authoritative public data model lives in `packages/autoresearch/src/literature/discovery/contracts.ts`; this document does not duplicate it. Task 2 consumes `DiscoveryConfig` (including `maxRequests` and `maxDurationMs`), `CurrentIdeaIdentity`, `DiscoveryProvider`, `DiscoverySourceStore`, `DiscoveryClock`, `SimilaritySurveyReport`, and `DiscoveryExecutionBinding`. The engine computes the semantic target with `fingerprintIdea(idea)` and keeps execution binding separate. Source capture uses `SourceRef` through `captureBytes`; integrations must provide a safe byte reader for rehash verification before sealing. Reports retain `collected`, `retained`, `omitted`, `shortlisted`, and `reviewed` counts and one explicit `stopReason`; the engine owns the exact union of allowed stop reasons.
The persisted checkpoint is separate from the compact report. Under `brainstorm/current-idea-survey/<ideaFingerprint>/<configFingerprint>/`, it stores completed queries, verified source references, the candidate pool, provider rate state, cumulative attempt/time budgets, model results, and separate pending HTTP/model dispatch markers. A verified durable receipt can recover without repeating its call. An unknown HTTP outcome is recorded and its exact request is not automatically repeated; an unknown model outcome remains paused without another paid dispatch. Corrupt source bytes fail verification. Bounded 429/5xx retries apply to known responses. Original dispatch timestamps remain immutable and an incremental accounting timestamp avoids charging an interval twice.

`fingerprintIdea` covers canonical statement, profile, scope, mechanism, prediction, falsification, measurement, decision rule, alternatives, assumptions, terminology, cross-domain analogs, and engine version. `configFingerprint` separately binds budgets, selected providers, parser version, and engine version. Their pair identifies a durable survey; run/cycle/source IDs are execution provenance and do not change semantic identity. A changed idea requires a fresh comparison. It may reuse age-bounded, hash-verified provider-query cache entries keyed by provider, request URL/parameters, and parser version. A different search policy cannot reuse an incompatible completed report.

Canonical identity deduplication is deterministic: normalized DOI first, then normalized arXiv ID, then provider ID, then normalized title plus first author and year. A merge retains all aliases and provider-hit receipts. Conflicting title, author, year, or abstract observations stay in the candidate's provenance and are exposed as uncertainty; they are not silently overwritten.

## Query and search flow

`literature/discovery/query-planner.ts` calls a model callback with the current idea and prior coverage. The default request is four query candidates spanning problem, mechanism, assumptions, terminology/synonyms, and cross-domain analogs. A host validator rejects malformed, empty, duplicate, or unbounded queries and caps the accepted set at `queriesPerRound`; the first round requires at least two distinct dimensions. If validation leaves fewer queries than requested, available valid queries still run, but the report records a coverage shortfall and remains partial. The host does not pay for an automatic planner replay to fill the shortfall. Injected fixture callbacks are deterministic; model output changes query wording, never source identity.

`literature/discovery/providers.ts` implements the authoritative `DiscoveryProvider` and `HttpReceipt` contracts. Each adapter stores bounded raw bytes through `ResearchStore.captureBytes`, captures decoded observations separately with parser provenance, and returns candidates tied to the receipt. Verification reads the actual captured `SourceRef` and rehashes its bytes. arXiv pagination uses `start`; Crossref uses bounded offset pagination; Semantic Scholar uses relevance search only. A 429 defers that provider according to `Retry-After` while other providers continue.

`literature/discovery/coordinator.ts` schedules providers round-robin with per-provider rate state. It honors `Retry-After`, retries only bounded 429/5xx responses, and records all other failures. It always completes the configured minimum three rounds unless a hard request, wall, abort, or provider-failure boundary intervenes; minimum rounds alone never cause a normal early finish. After the minimum, a documented low-yield/diversity condition may stop before five rounds. It never treats 200 candidates as a stop condition: 200 caps the retained, fused pool after required rounds and facet coverage, while later rounds may replace early literal decoys. Full bounded raw receipts and omitted counts remain available for audit. Hard budget exhaustion produces `partial`, not successful completion. `no_results` is a report status, not a novelty verdict. The coordinator archives the broader deduplicated pool and returns only the nearest configured slice to context.

`literature/discovery/reviewer.ts` calls an independent semantic reviewer with the current idea, candidate metadata/abstract excerpts, and receipt-backed IDs. The reviewer may compare only supplied candidate IDs and may suggest follow-up queries. The host validates candidate IDs, excerpt offsets/hashes, and citation-seed aliases before persisting the assessment. The report labels reviewer uncertainty and provider gaps; it never emits `supported`, `refuted`, `confirmed_error`, or a scientific evidence record.

Candidate ranking follows provider/query union. Reciprocal-rank fusion and a facet/provider exploration quota propose candidates for semantic review. The primary RRF reference is Cormack, Clarke, and Buettcher, [Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf), §1, which defines the sum `1/(60 + rank)`; exploration quotas are this feature's adaptation. Valid content-bound semantic judgments persist across rounds and influence retained/final-nearest selection before truncation. More query hits alone neither erase a known nearest paper nor demand another model review; materially new or conflicting observations are reconsidered alongside unexplored candidates. No literal-overlap minimum or blanket recency cutoff applies. The broad pool stays on disk. The report separates `collected`, `retained`, `omitted`, `shortlisted`, and `reviewed` counts; `nearest` is a bounded convenience view, not an exhaustive claim.

The same RRF paper, [§2](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf), states that it “combines ranks without regard to the arbitrary scores”. This matches ordinal fusion across providers whose scores are not directly comparable. Multiround search, exploration quotas, semantic-judgment retention and durable receipts are this project's adaptations, not mechanisms attributed to RRF or the earlier 2609 paper.

## Context, provenance, and corpus boundary

`literature/discovery/context.ts` turns the compact report into run-scoped `ContextRecord` values with `kind: 'artifact'`, `lifecycle: 'candidate'`, `polarity: 'neutral'`, and `accessRoles` limited to `planner`, `idea-generator`, `idea-reflexion`, and `hypothesis-reviser`. Payloads include the survey ID, candidate ID, canonical aliases, overlap, differences, uncertainty, provider receipt IDs, and exact excerpt proofs. Every record carries `SourceRef`s for the raw response, parsed excerpt, and reviewer report. The adapter captures those values with `ResearchStore.captureBytes`, then calls the injected `readSource(ref)` and rehashes the bytes before calling `sealContextRecord`; sealing alone does not prove a file's bytes. A required compact summary and closest-overlap excerpt set is selected within `maxContextChars`; overflow is reported explicitly. The binding carries the target fingerprint and is rejected when it does not match the current idea. The adapter does not create `RegisteredLiteratureSource` entries, `Evidence`, protocol allowlist IDs, or worker context.

`service/research-context.ts` adds this discovery package before its current no-snapshot/no-literature early return. `researchContextForInput` can therefore provide planner and idea roles with honest discovery context even when `literature.mode` is `off`; workers still receive no discovery records. `providers/subagent-provider.ts` adds a narrow discovery exposure receipt at the final prompt boundary. It records the selected artifact IDs, report hash, rendered prompt hash, and `sent`/`unknown` outcome without pretending that discovery artifacts are literature spans. A transport failure leaves the outcome `unknown` and does not promote the report to scientific evidence.

The default coordinator stores abstract excerpts in the run report only. It does not import them into the project corpus, build a generation, refresh a pinned generation, or change citation admission. Existing explicit library-ingest commands remain the route for a user who wants selected sources admitted; this feature adds no import UI. If a future caller supplies a corpus-admission callback, it must register candidate works and raw search receipts, ingest selected abstract text through `ingestDocument`, build and validate a new generation from registered spans, publish it, and call `updateLiteratureKnowledge` with a nonempty reason and existing source-event IDs before rebuilding context. That callback is outside the default survey path and must preserve the existing worker allowlist.

## Lifecycle semantics

The centralized planner seam in `experiment/steps.ts` resolves the current idea immediately before `runAgent` for `runPlanner` and `runMinimalPlan`. It runs the new targeted survey once for a given semantic target before the first planner, regardless of whether the idea came from the user or the brainstorm pipeline. This fixes the legacy `!shouldBrainstorm` gap without changing the existing `runInitialDeepDive` behavior or its tests. In minimal mode, the same seam runs before the minimal plan. The target comes from `ResearchStore.loadCurrent()` active hypothesis fields and the current decision candidate, falling back to the intake idea and profile before the first snapshot. That fallback is hashed as the initial target and is checked again immediately before context assembly, so a report can never be attached to a later, changed idea. `workflow.currentIdeaSearch: 'never'` is the explicit off switch; the production default is `'enabled'`. Existing `workflow.deepDive` semantics remain unchanged, including explicit `enabled` and `never` behavior; the new search is independent. Existing brainstorm disablement still suppresses brainstorm generation while allowing discovery of a supplied idea.

Historical frozen policies are immutable: if their policy snapshot lacks `currentIdeaSearch`, the runner does not retroactively enable network/model work. An existing run with no policy snapshot is also treated as historical and stays off. The new default applies only to newly normalized project settings and new runs; an audited policy update is required to opt an old run in.

At the start of each later cycle, the runner computes the semantic fingerprint from the selected/current hypothesis and revision text. A changed fingerprint runs a new survey before the planner freezes the next cycle. An unchanged fingerprint reuses its checkpoint and reviewer result without new HTTP or model calls. A current revision therefore invalidates only the relevant comparison, not the shared query cache. Terminal, paused, waiting, and frozen-experiment resume paths do not insert a new survey; a normal unchanged pause performs zero calls.

Planner context includes nearest work, overlap, differences, uncertainty, and coverage gaps. The permitted idea-generator, idea-reflexion and hypothesis-reviser roles can receive an existing report only when its target binding matches their current idea. Initial brainstorm/idea generation occurs before the planner hook, so that initial stage does not receive a newly generated current-idea report. These roles may revise an idea or request more discovery, but the host keeps admission and scientific assessment unchanged. Similarity cannot declare an idea refuted or confirmed, trigger cleanup or automatic candidate elimination, or satisfy a scientific criterion by itself.

## Settings and migration

Add a `currentIdeaSearch` toggle under `WorkflowSettings` and a `currentIdeaSearch` budget under `BudgetSettings`. Newly normalized settings migrate to:

```yaml
workflow:
  currentIdeaSearch: enabled
budget:
  currentIdeaSearch:
    minRounds: 3
    maxRounds: 5
    queriesPerRound: 4
    maxRequests: 80
    maxCandidates: 200
    maxDurationMs: 600000
    nearestLimit: 20
```

Validation requires integer bounds and `minRounds <= maxRounds`; `currentIdeaSearch: never` is the explicit off control. No API key is required. If an existing secure provider-key mechanism is later used for Semantic Scholar, it is read-only and optional; this feature does not add a secrets UI. Unknown settings still fail validation unless placed under the existing `extensions` namespace.

## Tests and controlled recall evidence

Unit tests cover query decomposition and validation, pagination, provider-specific response parsing, canonical DOI/arXiv/provider alias merging, rate limits and `Retry-After`, bounded retries, response-size limits, aborts, wall/request/candidate caps, checkpoint resume, changed-idea invalidation, forged receipt/candidate IDs, reviewer output validation, and the rule that an empty search cannot prove novelty. A fixture uses paraphrased abstracts for four known anchors: Macaroons (DOI `10.14722/ndss.2014.23212`), CaMeL (`arXiv:2503.18813`), RAG (`arXiv:2005.11401`), and REST (`arXiv:2311.08252`). The fixture does not copy long source text.

Integration tests cover a supplied idea, a post-brainstorm candidate, exactly one first search in legacy and minimal paths, a changed current hypothesis before a new planner freeze, zero calls for cached/WAITING/paper/terminal/PAUSED/frozen-experiment resumes, explicit search-off behavior, old frozen policies with missing search fields, and context roles that must not receive discovery artifacts. Existing live fixtures inject offline providers. A separate opt-in network smoke test records actual provider degradation and never counts unavailable providers as coverage.

The controlled recall report compares an explicitly constructed single literal-query reference against the varied multi-round controller across the known anchors. The reference is not the prior model-driven papersurvey implementation. This is a control-flow regression with deterministic provider responses and reviewer callbacks, not a measurement of live retrieval recall or model semantic quality. It records anchors collected, retained, shortlisted and reviewed, query/provider attempts, callback counts, literal decoys, and zero-call unchanged resume. The separate opt-in public-provider smoke records actual network outcomes without mixing them into fixture recall percentages.

## Risks and rollback

The main risk is provider instability or throttling; the report remains useful as a partial artifact and states which providers and rounds were unavailable. Forged candidate/excerpt output fails host source/hash validation. `workflow.currentIdeaSearch: never` disables the new search independently of the older deep-dive toggle. Historical frozen policies stay off unless explicitly updated. A crash inside stale-lock recovery leaves a recovery guard requiring explicit reconciliation rather than unsafe automatic lock stealing. Rollback removes the discovery stage and its settings migration; existing literature catalog rows, pinned generations, snapshots, evidence, and worker allowlists remain untouched.
